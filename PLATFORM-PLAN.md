# The Flow Labs — Platform Plan

Dynamic site + Flow HQ admin + internal team & project management.

Status: **plan for approval**. No production code changed by this document.
Stack decisions confirmed: extend Vercel + Supabase · static shell + live content ·
GitHub App + webhooks · team lives inside `/flow-hq` · Phase 1 = database/auth/roles ·
existing SMTP · scheduled `pg_dump` backups · Vercel Hobby.

Added after review: a **client portal** with admin-issued client accounts and a
read-only view of delivery status, and a **rebuild of the Content and Settings
screens**, which are currently the weakest part of Flow HQ.

Accounts (team and client) are **created by an admin**. There is no self-signup,
no public registration, and no invitation flow a stranger can trigger.

### 1.2 Flow HQ today

`/flow-hq/` is a vanilla-JS admin panel with six tabs — Dashboard, Leads, Visitors,
Content, Blog, Settings — driven by `flow-hq/admin.js` (~39 KB) and
`flow-hq/content-schema.js`. Auth is already real: Supabase session, then an
`is_admin()` RPC gate; sign-out on failure.

This is a genuine asset. It is not a mockup, and it already writes to the database.

### 1.3 What is reusable as-is (do not rebuild)

1. **Supabase Postgres + Auth + RLS.** The entire security model we need already
   has a foundation: JWT sessions, row-level policies, `is_admin()`.
2. **Flow HQ shell.** Nav, tabs, tables, drawers, toasts, login screen, styling.
3. **CMS override layer.** `site_content` + `data-cms` attributes + `site-cms.js`
   fetch-and-replace. Editing copy already needs no deploy.
4. **Settings layer.** `site_settings` drives accent colour, section toggles, SEO
   defaults at runtime.
5. **Lead pipeline.** Capture, admin read/update/delete, email notify via
   `api/notify.js` + nodemailer.
6. **Analytics.** Cookie-less `site_visitors` + `visitor_stats()` RPC.
7. **Lab Report.** `/api/audit` works and caches to `site_audits`.
8. **Blog data model** (`supabase-blog.sql`, currently uncommitted): posts, drafts,
   `status`, `published_at`, tags, SEO fields. Editor UI already exists.
9. **Headers, redirects, noindex rules** in `vercel.json`.

### 1.4 Gaps that block the brief

| Gap | Evidence | Consequence |
|---|---|---|
| CMS covers **4 pages only** | `PAGE_MAP` in `assets/site-cms.js` = `/`, `/about`, `/services`, `/contact` | The other ~20 pages have no live editing, even where `data-cms` attributes exist |
| Blog publish requires **a redeploy** | `api/rebuild.js` fires a Vercel deploy hook; posts render only after rebuild | Violates "live without redeployment" |
| No team identity | `admin_users` is a flat email allowlist | No roles, no per-project access, no invites |
| No client access | Clients have no identity or view at all | Cannot show delivery status without exposing internal tasks |
| No project/module/task schema | Nothing beyond site tables | The core product does not exist yet |
| No server-side authorisation helper | Only `is_admin()` | Cannot express "member of this project/module" in RLS |
| No audit trail | Only `site_audits` (Lighthouse scans) | No who-changed-what record |
| No file storage | Uploads unused | Document sharing needs a bucket + policies |
| No realtime | Everything is fetch-on-load | Comments/activity would be stale |
| Function budget | 5 live functions, 6 in tree | Vercel Hobby caps at 12 per deployment |

### 1.5 Two constraints that shape the design

**Vercel Hobby allows 12 serverless functions per deployment.** A naive build would
add 25+ endpoint files. Mitigation: **one catch-all router** at
`api/platform/[...path].js` plus the six existing functions — 7 total. If timeouts
or concurrency become a limit, Vercel Pro lifts both.

**A static `<title>` cannot be edited without new HTML.** Body copy is instant via
the CMS overlay. Meta/SEO changes need server-rendered HTML for crawlers. We will
write meta live to the DOM *and* trigger a debounced automatic rebuild — no manual
deploy, but crawler-visible within roughly a minute.

## 2. Target architecture

```
Browser ──┬─ static HTML + site.css/site.js  (unchanged design)
          ├─ site-cms.js ── GET /api/content, /api/settings   (live copy)
          └─ /flow-hq app ── supabase-js (JWT)
                                  │
                                  ├─ PostgREST reads/writes ── RLS ── Postgres
                                  └─ /api/platform/* (router) ── service role
                                          ├─ invites, GitHub, uploads, email
                                          └─ audit + notification fan-out

GitHub ── webhook ── /api/platform/github/webhook ── verify HMAC ── Postgres
                                   └─ Realtime ── project members' dashboards
```

Design rule: **the browser talks to PostgREST directly for ordinary CRUD**, with
RLS as the security boundary. Server routes exist only for operations that need
the service role or a secret: invites, GitHub, file signing, email, audit export,
bulk admin actions. That keeps the function count low and reads fast.

## 3. Data model

New namespace `public`, all tables RLS-enabled. Migrations live in
`supabase/migrations/NNNN_name.sql`, idempotent, forward-only.

### 3.1 Identity and access

```sql
create type app_role      as enum ('owner','admin','manager','member','client');
create type member_status as enum ('invited','active','suspended');
create type project_role  as enum ('manager','member','viewer');

create table profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  email text not null unique,
  full_name text,
  avatar_url text,
  role app_role not null default 'member',
  status member_status not null default 'invited',
  github_username text,
  timezone text default 'Asia/Kolkata',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table project_members (
  project_id uuid references projects(id) on delete cascade,
  user_id uuid references profiles(id) on delete cascade,
  role project_role not null default 'member',
  added_by uuid references profiles(id),
  created_at timestamptz not null default now(),
  primary key (project_id, user_id)
);

create table module_members (
  module_id uuid references modules(id) on delete cascade,
  user_id uuid references profiles(id) on delete cascade,
  primary key (module_id, user_id)
);
```

Client accounts are `profiles.role = 'client'` plus a row in `project_clients`. They
are deliberately **not** in `project_members`: staff helpers ignore them, and client
helpers read a different table, so a client can never inherit task, comment or commit
visibility through a shared membership row.

`admin_users` stays in place for compatibility; existing emails are seeded into
`profiles` with `role='admin'`, and `is_admin()` is redefined to read `profiles`.
That ordering matters — redefining it before seeding would lock everyone out.

### 3.2 Work

```sql
projects   (id, key, slug, name, summary, description, status, priority,
            owner_id, start_date, due_date, created_by, timestamps)
modules    (id, project_id, name, description, status, position, lead_id,
            start_date, due_date, timestamps)
tasks      (id, project_id, module_id, number, key, title, description,
            status, priority, assignee_id, reporter_id, due_date,
            estimate_hours, position, completed_at, timestamps)
task_comments (id, task_id, author_id, body, timestamps)
daily_reports (id, user_id, project_id, report_date, summary, blockers, hours,
               timestamps)  unique (user_id, project_id, report_date)
attachments   (id, project_id, module_id, task_id, uploader_id, bucket, path,
               file_name, mime, bytes, client_visible boolean default false, created_at)
```

`projects.key` (e.g. `FLW`) + `tasks.number` produce `FLW-42`, which is the join
key for GitHub commits and PR titles.

Statuses: task `backlog | todo | in_progress | review | blocked | done`;
project/module `planning | active | on_hold | completed | archived`.

### 3.3 Collaboration

```sql
notifications (id, user_id, kind, title, body, link, project_id, read_at, created_at)

activity      (id, project_id, actor_id, verb, entity_type, entity_id,
               summary, meta jsonb, created_at)

project_clients (project_id, user_id, created_at)   primary key (project_id, user_id)

client_updates  (id, project_id, title, body, author_id, published_at, created_at)
```

Clients see exactly four things for their own projects: overall status and dates,
module names with status and progress, published `client_updates`, and attachments
with `client_visible = true`. They never see tasks, comments, commits, pull requests,
daily reports, member activity or other projects. This is enforced in RLS, not in
the UI.

`activity` is one append-only feed table rather than five per-entity tables. Verbs:
`task.created`, `task.moved`, `task.assigned`, `comment.added`, `module.created`,
`report.submitted`, `file.uploaded`, `commit.pushed`, `pr.opened`, `pr.merged`,
`member.added`.

### 3.4 GitHub

```sql
github_repos        (id, project_id, installation_id, repo_full_name,
                     default_branch, linked_by, created_at)  unique(repo_full_name)
github_commits      (id, project_id, repo_full_name, sha, branch, message,
                     author_name, author_email, author_login, author_id,
                     committed_at, url)  unique(repo_full_name, sha)
github_pull_requests(id, project_id, repo_full_name, number, title, state, draft,
                     author_login, author_id, head_ref, base_ref, url,
                     opened_at, merged_at, closed_at)  unique(repo_full_name, number)
task_links          (task_id, kind, ref)  primary key (task_id, kind, ref)
github_events       (id, delivery_id unique, event, payload jsonb, received_at,
                     processed_at, error)
```

`github_events` is the raw webhook log — replayable, and the reason a bad payload
never loses data.

### 3.5 Ops

```sql
audit_log (id, actor_id, actor_email, action, entity_type, entity_id,
           before jsonb, after jsonb, ip inet, user_agent text, created_at)
```

Written by triggers for direct PostgREST mutations and by the router for
privileged operations. Never writable by clients.

### 4.1 Matrix

| Capability | Owner | Admin | Project manager | Member | Viewer | Client |
|---|---|---|---|---|---|---|
| Site content, blog, settings | ✓ | ✓ | — | — | — | — |
| Leads, visitors, lab reports | ✓ | ✓ | — | — | — | — |
| Create / archive projects | ✓ | ✓ | — | — | — | — |
| Edit own project, members | ✓ | ✓ | ✓ | — | — | — |
| Modules, tasks, Kanban | ✓ | ✓ | ✓ | assigned | — | — |
| Assign tasks to others | ✓ | ✓ | ✓ | — | — | — |
| Comment, upload, daily report | ✓ | ✓ | ✓ | ✓ | — | — |
| View commits/PRs/activity | ✓ | ✓ | ✓ | ✓ | ✓ | — |
| Invite/remove team, change roles | ✓ | ✓ | — | — | — | — |
| Link GitHub repos | ✓ | ✓ | ✓ | — | — | — |
| Audit log | ✓ | ✓ | — | — | — | — |
| Project status, modules, progress | ✓ | ✓ | ✓ | ✓ | ✓ | own projects |
| Publish client updates | ✓ | ✓ | ✓ | — | — | — |
| Client-visible files | ✓ | ✓ | ✓ | ✓ | — | own projects |

### 4.2 RLS helpers

All `security definer`, `stable`, `set search_path = public`, so they bypass RLS
internally and cannot recurse:

```sql
current_role()            -- app_role of auth.uid(), null if suspended
is_admin()                -- owner/admin, redefined over profiles
can_access_project(uuid)  -- staff only: admin, project owner, or project_members row
can_manage_project(uuid)  -- admin or project_members.role = 'manager'
can_access_module(uuid)   -- project access + module rule below
can_access_task(uuid)     -- project access + module rule below
is_client_of(uuid)        -- profiles.role = 'client' AND project_clients row
```

Module rule, stated once and documented in the UI:

> A member with **no** `module_members` rows in a project sees the whole project.
> Once the admin assigns them to specific modules, they see only those modules and
> their tasks. Task with `module_id = null` is project-level and visible to anyone
> with project access.

Every table gets four explicit policies. No `using (true)` except public reads of
published blog posts, public content/settings, and anon lead insert — matching
today's behaviour.

### 4.3 Server-side validation

Two independent layers, both required:

1. **RLS** — even a forged request through PostgREST returns zero rows.
2. **Router checks** — verify the JWT with `auth.getUser(token)`, load the profile,
   check role and project membership *before* using the service key.

The workspace script `scripts/rls-test.mjs` asserts, against a preview project:
anon cannot read tasks; member A gets 0 rows for project B; a member cannot
`UPDATE profiles.role`; a non-manager cannot insert a module.

## 5. API surface

One router: `api/platform/[...path].js`. Direct PostgREST handles reads/writes that
RLS already protects.

```
GET    /api/platform/me
GET    /api/platform/bootstrap            -- profile, projects, unread count
POST   /api/platform/team/invite          -- service role: auth invite + profile
PATCH  /api/platform/team/:id             -- role/status change
POST   /api/platform/uploads/sign          -- signed upload URL
GET    /api/platform/github/install        -- redirect to GitHub App install
GET    /api/platform/github/callback       -- store installation_id
POST   /api/platform/github/webhook        -- HMAC, no session
POST   /api/platform/github/sync           -- backfill recent commits
GET    /api/platform/audit                 -- filtered, admin only
POST   /api/platform/reports/notify        -- email digest via nodemailer
```

Everything else — projects, modules, tasks, comments, reports, notifications,
attachments, activity — goes browser → PostgREST under RLS. This is deliberate:
fewer functions, no N+1 proxying, and the database is the enforcement point.

Mutations that need side effects (notifications, activity, audit) are handled by
`after` triggers, so they cannot be bypassed by writing through a different path.

## 6. Live content

### 6.1 All pages, not four

1. `tools/site/cms_registry.py` scans every built page for `data-cms` keys and
   emits `flow-hq/cms-registry.js` (page → fields, with defaults read from HTML).
2. `PAGE_MAP` is replaced by `document.body.dataset.page` (already emitted by the
   generator), so every page resolves.
3. Flow HQ's Content tab renders groups from the registry, not a hand-written list.
4. Add `data-cms` bindings to the currently unbound headings, service cards, FAQ
   answers, and legal body copy.

Exit criterion: edit a paragraph on `/work/droovee/` in Flow HQ, refresh, see it —
no deploy.

### 6.2 Meta and SEO

`site_content` gains `meta_title`, `meta_description`, `og_image` rows per page.
`site-cms.js` applies them to the DOM immediately. A debounced call to
`/api/rebuild` regenerates static HTML so crawlers see the same title. The admin
shows "Visible now · crawlable in ~1 min" so the behaviour is honest, not magic.

### 6.3 Blog without redeploys

- `site_blog_posts` remains the source of truth; extend with `cover_alt`,
  `seo_title`, `canonical`, `author_id`, `rendered_at`.
- New `api/blog-page.js` renders `/blog` and `/blog/:slug` from the database,
  reusing the existing article template and CSS. Edge cache
  `s-maxage=60, stale-while-revalidate=600`.
- Bundled JSON snapshot of `blog-src/*.md` is the fallback if the DB is unreachable,
  so a database incident does not 404 the blog.
- Draft preview at `/blog/preview?token=…`, signed, `noindex`, 15-minute expiry.
- `api/rebuild.js` stays as a safety net but is no longer on the publish path.

## 7. Flow HQ UI plan

Keep the current shell, tokens and login. Add tabs by role.

**Admin:** Overview · Leads · Visitors · Content · Blog · Projects · Team · GitHub ·
Reports · Activity · Settings
**Member:** My work · My projects · Reports · Notifications · Profile

New surfaces:

- **Projects list** — status, progress bar, members, due date; create/archive.
- **Project view** — tabs for Board, Modules, Tasks, Activity, Files, Settings.
- **Kanban** — columns by status, drag and drop plus a keyboard/“Move to…”
  menu (drag alone is not accessible), WIP counts, filters by assignee/module.
- **Task drawer** — description, assignee, priority, due date, comments, linked
  commits/PRs, attachments, activity.
- **GitHub** — repo links, connection health, unattributed commit mapping.
- **Reports** — daily report form pre-filled from the day’s commits/PRs; weekly
  rollup per member and per project.
- **Notifications** — bell + inbox, realtime badge, email digest opt-in.

Responsive: board scrolls horizontally on mobile; nav collapses to a drawer; tables
become cards under 720 px. Reuse `admin.css` tokens (`--accent`, `--bg`, `--border`)
so it looks like the same product.

### 7.1 Why Content and Settings feel unfinished

Reading the current markup in `flow-hq/index.html`:

- **Content** is a page `<select>` above one long form. No search, no grouping, no
  field count, no section anchors. At 24 pages and 100+ fields it becomes a scroll hunt.
- The "preview" is a text dump in a side box, not the page the visitor sees.
- Save sits at the bottom of a long card. There is no dirty-state indicator, no
  unsaved-changes warning, and no per-field reset.
- **Reset page** — destructive, no undo — sits next to **Open page**.
- The hint says "changes go live within about 60 seconds" and "blank fields fall back
  to the hardcoded HTML". That is implementation language, not an admin's language.
- **Settings** is one form for accent, section toggles and SEO, with one Save for all
  three. Nothing saves independently.
- The accent control is a colour input plus a hex box with no contrast check.
- Section toggles render into an empty `<div>` with no explanation of what disappears
  when switched off.
- The SEO panel literally tells the admin to edit `tools/site/build.py`. That single
  line is the clearest sign the panel is half-built.
- No integration health, no backup status, no danger zone.

### 7.2 Content and Settings rebuild

**Content**

- Two-pane layout: left is a searchable page tree grouped Site / Services / Work /
  Blog / Legal, with an "edited" dot per page; right is the field editor grouped into
  collapsible sections.
- Sticky action bar: page name, dirty count ("3 unsaved changes"), Discard, Save.
  Warn before navigating away with unsaved work.
- Per field: current value, default value, **Reset to default**, and a character
  counter on SEO fields. Formatting hints appear only where HTML/Markdown is allowed.
- Live preview: an `<iframe>` of the real page at desktop and mobile widths. Unsaved
  edits render through the same override path, so the preview is truthful.
- Empty state for pages without editable fields yet, instead of a blank form.

**Settings**

- Section rail instead of one form: Brand, Homepage sections, SEO defaults,
  Integrations, Backups, Danger zone. Each section saves independently and reports
  success or failure inline.
- Accent: swatches plus custom hex, with a live contrast check against the page
  background. Warn below 4.5:1 for body text.
- Section toggles: each row shows the section name, a one-line description, and what
  it controls. No mystery checkboxes.
- SEO: title and description with a search-result preview and an honest
  "crawler-visible after rebuild" status.
- Integrations: read-only health for Supabase, SMTP last send, GitHub App install and
  last webhook, deploy hook last fired. Secrets stay in Vercel; the panel never shows
  them.
- Danger zone: export all content as JSON, reset overrides page by page, typed
  confirmation for anything destructive.

### 7.3 Client portal

A separate, small surface at `/client/` — same design tokens, none of the admin code.

- **Login:** admin-issued email + temporary password; password reset by email.
- **Dashboard:** every project the client is linked to, with overall status, progress,
  next milestone and the latest update.
- **Project view:** status timeline, module list with progress, published updates,
  shared files. Nothing else.
- **Never visible:** tasks, task comments, commits, pull requests, daily reports,
  team activity, other clients, other projects.
- **Admin side:** Project → Client access → create account, link project, post an
  update, mark a file client-visible, revoke access. Revoking removes the
  `project_clients` row and the client loses access on the next request.

The client page is its own HTML entry so a client session never downloads the admin
bundle. The same Supabase project is used; RLS is what actually protects the data.

## 8. GitHub integration

1. Create a **GitHub App** (not an OAuth app): permissions `Contents: read`,
   `Pull requests: read`, `Metadata: read`; events `push`, `pull_request`,
   `create`, `delete`.
2. Admin installs it on selected repos from Flow HQ → stored `installation_id`.
3. Webhook → `/api/platform/github/webhook`:
   - verify `X-Hub-Signature-256` with the app secret,
   - insert into `github_events` keyed by `X-GitHub-Delivery` (idempotent),
   - return `200` immediately, process inline in under a second (single insert +
     attribution; backfill uses `/sync`).
4. Attribution order: commit author email → `profiles.email`; else
   `author_login` → `profiles.github_username`; else store unattributed and surface
   a “map this author” action.
5. Task linking: match `FLW-\d+` in commit message, branch name, PR title or body →
   `task_links`; the task drawer shows the commit/PR list.
6. Daily report draft: today’s commits and PRs grouped by project, member edits and
   submits. Nothing is auto-submitted on their behalf.

Secrets (`GITHUB_APP_ID`, `GITHUB_PRIVATE_KEY`, `GITHUB_WEBHOOK_SECRET`) are Vercel
env vars, never in the repo.

## 9. Database operations

- **Migrations:** `supabase/migrations/0001_identity.sql` … forward-only, wrapped in
  transactions, applied via Supabase CLI against a staging project first.
- **Backups:** nightly GitHub Action runs `pg_dump` over the session pooler, encrypts
  with `age`, stores 30 daily + 12 monthly copies off-site, and fails loudly. A
  documented restore drill runs once before go-live.
- **Retention:** `github_events` 90 days, `activity` 24 months, `audit_log` 12 months
  (configurable).
- **Seeding:** existing `admin_users` emails → `profiles`; existing posts → no change;
  existing CMS rows untouched.
- **Connection strings:** serverless work uses the Supavisor pooler
  (`...pooler.supabase.com:6543`, transaction mode), never the direct `db.<ref>` host,
  which is IPv6-only on newer projects. Passwords with `@`, `:`, `/` or `#` must be
  percent-encoded or a URI parse fails silently.
- **Credentials:** never in chat, never in the repo, never in a client bundle. Local
  values live in `.env.local` (already gitignored). Any credential pasted into a
  conversation is rotated, not reused.

## 10. Security checklist

- [ ] RLS on every table; default deny; four policies each
- [ ] `security definer` helpers with pinned `search_path`
- [ ] Service-role key only in Vercel env; never in client bundles
- [ ] JWT verified server-side on every privileged route
- [ ] Webhook HMAC + replay protection (`delivery_id` unique)
- [ ] Input validation and length caps on every text field
- [ ] Upload allowlist (pdf, png, jpg, webp, docx, xlsx, md), 25 MB cap, private bucket
- [ ] Signed URLs, 60-second expiry
- [ ] Rate limiting on `/api/*` at Cloudflare (already proxying) + per-user writes
- [ ] CSP `connect-src` extended to `https://<ref>.supabase.co wss://<ref>.supabase.co`
- [ ] Session expiry and forced sign-out on `status='suspended'`
- [ ] Audit every role, membership and permission change
- [ ] No secrets in logs; webhook payloads redacted before logging

## 11. Phases

Estimates assume one developer, existing design retained, and are ranges.

### Phase 0 — Safety and baseline (0.5 day)

- Commit the verified Bhubaneswar/local-SEO work **separately** from platform work.
- Branch `platform/v1`; snapshot the current database.
- Add `supabase/migrations/`, `scripts/`, `.env` keys; pin dependencies.
- Add `audit_log` + `schema_migrations` first, before any other table.

**Exit:** production unchanged except the SEO commit; a restore from the snapshot
has been verified.

### Phase 1 — Database, auth, roles (3–4 days)

- Schema: `profiles`, `project_members`, `module_members`, helper functions.
- Seed admins; redefine `is_admin()`; keep old admin paths working.
- Invite flow through `/api/platform/team/invite` + Supabase Auth + custom SMTP.
- Role-aware Flow HQ shell: member nav, admin nav, route guards.
- RLS test suite green against the real project.

**Exit:** an invited member can sign in, sees only their projects (zero rows
otherwise), and cannot escalate their own role.

### Phase 2 — Content, blog, and the admin rebuild (5 days)

- CMS registry, all pages editable, meta fields.
- Content tab rebuilt: searchable page tree, grouped fields, dirty state, live iframe
  preview, per-field reset.
- Settings tab rebuilt: section rail, independent saves, contrast check, integration
  health, danger zone.
- Dynamic `/blog` + `/blog/:slug` renderer with snapshot fallback and draft preview.
- Media uploads to Storage; cover images and alt text.
- Debounced rebuild for crawler-visible meta.

**Exit:** publish a post and see it live in under 5 seconds; edit a paragraph on any
page and see it without a deploy.

### Phase 3 — Projects, modules, tasks (4–5 days)

- Projects/modules CRUD, membership UI, per-project permissions.
- Kanban with drag + keyboard move, filters, WIP counts.
- Task drawer, comments, attachments, activity feed, progress bars.
- Member “My work” view across projects.

**Exit:** two members on different projects cannot see each other’s tasks through
the API; board state survives reload; progress matches task counts.

### Phase 4 — Client portal (2 days)

- `client` role, `project_clients`, `client_updates`, client-visible files.
- Admin: create client account with a temporary password (shown once, copyable),
  link to project, post updates, revoke.
- `/client/` shell: dashboard, project status, module progress, updates, files.
- RLS tests proving a client gets zero rows from tasks, comments, activity,
  notifications and other projects.

**Exit:** a client signs in, sees only their project’s status and updates, and cannot
